[https://github.com/erlef/setup-beam/blob/main/SECURITY.md](https://github.com/erlef/setup-beam/blob/main/SECURITY.md)

Please follow the process described there rather than opening a public issue for security-sensitive reports.

## The `github-token` input

`setup-beam` accepts an optional `github-token` input used when querying the GitHub REST API to resolve tool versions (Erlang/OTP, Elixir, Gleam, rebar3 release metadata). The action performs **read-only** operations only — it never writes to your repository, creates releases, or modifies any resources.

Because only read access is required, the default token that GitHub Actions injects into every workflow job is sufficient:

```yaml
- uses: erlef/setup-beam@v1
  with:
    otp-version: '27'
    elixir-version: '1.18'
    github-token: ${{ github.token }}  # default; often omitted entirely
```

<Note>
  You do not need to pass `github-token` explicitly. If the input is omitted, the action uses the same `${{ github.token }}` automatically.
</Note>

<Warning>
  Do not supply a personal access token with broader scope than necessary. The `${{ github.token }}` provided by GitHub Actions is scoped to the current repository and expires when the workflow job finishes — it is the safest option.
</Warning>

## Pinning to a specific version

For security-sensitive environments, pin `setup-beam` to an exact release tag (for example `@v1.8.0`) or to a full commit SHA. This ensures that the action code cannot change underneath you if a movable tag like `@v1` is updated.

```yaml
# Pinned to an exact release — recommended for security-conscious workflows
- uses: erlef/setup-beam@v1.8.0
```

See [release versioning](/project/versioning) for a full explanation of the tag strategies available.
